# Spring Boot Crash Course for Beginners

Welcome to the backend of the Library Management System (LMS)! This application is built using Java and the Spring Boot framework.

If you've never used Spring Boot before, don't worry! This guide is designed to explain the core concepts, the syntax, and the architecture you'll encounter in this project so you can hit the ground running.

---

## 1. What is Spring Boot?

Spring is a massive ecosystem for building enterprise Java applications. However, setting up a bare Spring application requires a lot of configuration. 

**Spring Boot** is an extension of the Spring framework that provides "auto-configuration." It looks at the libraries (dependencies) you include in your project and automatically configures your application based on common defaults. 

Think of it this way: **Spring Boot provides the scaffolding and plumbing, so you can focus strictly on the business logic (like borrowing a book).**

---

## 2. The Core Concept: Inversion of Control (IoC) & Dependency Injection (DI)

### The Problem:
Normally, if a `Controller` needs a `Service` to do some work, you would write:
```java
BookService service = new BookService(); // Tightly coupled!
```
This tightly couples your code, making it hard to test and maintain.

### The Spring Solution:
Spring acts as a giant "Container." When the application starts, Spring creates all your objects (called **Beans**) and wires them together. This is called **Dependency Injection**.

You simply tell Spring, "Hey, this class needs a `BookService`," and Spring will hand it to you automatically.

### How we do it using annotations:
```java
@Service // Tells Spring: "Make this a Bean"
public class BookService {
    // ...
}

@RestController // Tells Spring: "This is a Bean that handles web requests"
@RequiredArgsConstructor // Automatically creates a constructor for all 'final' fields (via Lombok)
public class BookController {

    // Spring sees this constructor (generated by Lombok) and automatically injects the BookService!
    private final BookService bookService; 

    // ...
}
```

## 3. The Layered Architecture

Our backend strictly follows the **Layered Architecture Pattern** (Controller → Service → Repository). This is non-negotiable.

### Layer 1: The Repository (`com.lms.repositories`)
**Job:** Talk to the Database.
Spring Data JPA makes this incredibly easy. You just define an interface and extend `JpaRepository`. Spring automatically implements all the CRUD (Create, Read, Update, Delete) queries for you!
```java
public interface BookRepository extends JpaRepository<Book, Long> {
    // Spring knows how to execute this just based on the method name!
    Optional<Book> findByIsbn(String isbn);
}
```

### Layer 2: The Service (`com.lms.services`)
**Job:** Business Logic.
This is where the "thinking" happens. Controllers ask the Service to do things, and the Service coordinates with the Repositories.
```java
@Service
@RequiredArgsConstructor
public class LoanService {
    private final BookRepository bookRepository;

    public void borrowBook(Long bookId) {
        Book book = bookRepository.findById(bookId).orElseThrow();
        if (book.getAvailableCopies() <= 0) {
            throw new RuntimeException("No copies available!");
        }
        // ... create loan ...
    }
}
```

### Layer 3: The Controller (`com.lms.controllers`)
**Job:** Handle HTTP Requests and Responses.
Controllers are dumb. They should ONLY receive a web request (like a POST or GET), parse the incoming data, call a Service, and return a response (like JSON). No business logic allowed!
```java
@RestController
@RequestMapping("/api/v1/books") // Base URL for this controller
public class BookController {
    
    // ...

    @GetMapping("/{id}") // Maps a GET request to /api/v1/books/1
    public ResponseEntity<BookResponseDTO> getBook(@PathVariable Long id) {
        return ResponseEntity.ok(bookService.getBookById(id));
    }
}
```

## 4. DTOs vs Entities

### Entities (`com.lms.entities`)
Entities are Java classes mapped directly to database tables using JPA/Hibernate annotations (`@Entity`, `@Table`, `@Id`). They represent the exact structure of your database.

### DTOs (Data Transfer Objects) (`com.lms.dtos`)
DTOs are simple objects used to pass data between the client (React frontend) and the server (Spring Boot backend). 

**The Rule:** *Never expose Entities directly from Controllers.* 
Why? Because an Entity might contain sensitive data (like a user's password) or trigger infinite loops when serialized to JSON (if Book links to Author, and Author links back to Book).

Instead, Services convert Entities into DTOs before returning them to the Controller.

## 5. Security & JWT

Our backend is secured using **Spring Security** and **JSON Web Tokens (JWT)**.
1. When a user logs in via `AuthController`, the `AuthService` verifies their password.
2. If valid, a JWT (a signed string containing the user's ID and Role) is generated and returned to the client.
3. For all future requests, the client sends this JWT in the `Authorization: Bearer <token>` header.
4. The `JwtAuthenticationFilter` intercepts the request, validates the token signature, and tells Spring Security who the user is.
5. Controllers use `@PreAuthorize("hasRole('ADMIN')")` to restrict access based on the user's role.

## 6. Lombok

You'll see annotations like `@Data`, `@Builder`, `@NoArgsConstructor`, and `@RequiredArgsConstructor` everywhere. These come from a library called **Lombok**.

Lombok plugs into your compiler and automatically generates boilerplate code (like Getters, Setters, Constructors, and Builders) so your classes stay clean and concise.

*Example:* Adding `@Data` to a class automatically gives it a getter and setter for every field!

---

## Conclusion
By keeping your Controllers focused on HTTP, your Services focused on rules, your Repositories focused on data, and using DTOs to communicate, the codebase remains clean, testable, and highly scalable. Welcome to Spring Boot!
